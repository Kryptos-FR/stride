# Avalonia UI for Stride games (prototype)

`Stride.AvaloniaUI` lets a game write its UI with Avalonia (XAML, controls, styles, bindings) and draws it with Stride. It is an alternative to `Stride.UI`, not part of it: a game uses one or the other.

## Using it

Reference `Stride.AvaloniaUI` and `Stride.AvaloniaUI.Skia` from the game, then add an **Avalonia UI** component to an entity of the scene:

- `ViewType`: the type of a control to show, such as a `UserControl` written in XAML (`MyGame.Views.MainMenu, MyGame`), or
- `Content`: a control set from a script, which takes precedence.

The placement properties keep the names and meaning of `UIComponent`'s: `Resolution` (virtual resolution, 1280x720 by default) and `ResolutionStretch`. `DrawOrder` orders several views: the higher one is drawn on top and gets the input first.

A game that doesn't set up Avalonia gets the Fluent theme, dark, with the Inter font, and the Skia renderer, found among the packages the game references. To use its own application (resources, styles, theme), the game sets Avalonia up on the game thread before it runs:

```csharp
AppBuilder.Configure<MyApp>().UseStride().WithInterFont().SetupWithoutStarting();
using var game = new Game();
game.Run();
```

The native renderer, Stride's own, is opt-in: such a game sets Avalonia up with `UseStride(AvaloniaUIRenderer.Native)`. It draws rectangles, rounded rectangles, borders of even thickness, ellipses and lines with solid colors, under rectangle and rounded rectangle clips, on the game's device with Direct3D 11, Direct3D 12 and Vulkan at graphics profile `Level_10_0` or above. It hands everything else to the Skia package, which draws it on the CPU, in place, so the game still needs that package. With `RenderOnGpu` false, or on another device, the Skia package draws whole frames on the CPU.

## How it works

- Two packages: `Stride.AvaloniaUI` (the platform, the component and the game system; no Skia) and `Stride.AvaloniaUI.Skia` (the Skia renderer). The renderer is chosen once per process when Avalonia is set up (`UseStride(renderer)`), as Avalonia has one render interface per process. The core finds the Skia package among the registered assemblies, through its `[AssemblyScan]` index, or gets it from `UseSkiaFallback()` on the `AppBuilder`.
- `Platform/`: an Avalonia platform with no native windows. Avalonia's dispatcher and render loop run on the game thread, driven by the game loop (`StrideDispatcherImpl`, `StrideRenderTimer`). Each view is an offscreen top level (`StrideTopLevelImpl`).
- `Stride.AvaloniaUI.Skia/WholeFrame/`: Skia draws whole frames (`SkiaRendererBackend`), on the game's own Vulkan device. Skia renders each view into a texture of the device, with the device's queue, and the game draws that texture without a copy. Avalonia takes it as the GPU of its Skia backend (`StrideSkiaGpu`, given through `SkiaGpuProxy`); `Stride.Graphics` gives the Vulkan handles Skia needs (`VulkanInterop`). On macOS the device runs on Metal (MoltenVK) and SkiaSharp has no Vulkan: Skia draws with Metal, on the `MTLDevice`, `MTLCommandQueue` and `MTLTexture` behind the device's objects, which `VulkanInterop` exports (`VK_EXT_metal_objects`). Where Skia can't share the device, it renders on the CPU into memory that keeps the previous frame, and the game uploads the frames that changed.
- `Rendering/`: the native renderer (`NativeRendererBackend`). Avalonia's geometry, bitmaps and glyph runs are the core's own (`StrideRenderInterface`). On the CPU, the drawing context records each frame's calls (`RecordingDrawingContext`) for a fallback to draw (`IRenderFallback`). The Skia package's fallback converts the core's objects to Skia's and draws the calls into the frame's memory with Skia's own drawing context (`Stride.AvaloniaUI.Skia/Fallback/`).
- `Rendering/Native/`: the native canvas, on the game's device. Each view draws into a texture of the device kept between frames (`NativeTextureRenderTarget`), through `NativeDrawingContext`. The shapes `NativeShapes` knows become instanced quads (`CanvasBatch`) of the canvas shader, `Shaders/AvaloniaCanvasShader.sdsl`, which covers each pixel by its distance to the shape's outline, under a scissor or under a clip the shader draws. The other calls go to the fallback in runs (`FallbackRun`), drawn on the CPU and then in place as images, and are counted by the reason they went there (`FallbackReason`). The shader is precompiled and embedded for each graphics API (`Shaders.Bytecodes/`); a graphics API without bytecode draws on the CPU. After a change of the shader, `dotnet test sources/shaders/Stride.Shaders.Tests -p:StrideSkipPrecompiledBytecodeCheck=true --filter "FullyQualifiedName~EmbeddedEffectTests.UpdateEmbeddedEffects" -- xUnit.Explicit=on` makes the bytecode again: on Windows for Direct3D, and on Linux, with `-p:StridePlatforms=Linux -p:StrideGraphicsApis=Vulkan`, for Vulkan. `EmbeddedEffectsAreCurrent` checks it is current.
- `AvaloniaUISystem` (a `[GameSystem]`): pumps Avalonia in the update, renders the views in the draw, and draws their frames over the back buffer after the scene. `RenderOnGpu` (on by default) chooses Skia on the device or on the CPU; a change takes effect at the next frame.
- Input goes through the `InputManager`'s capture: a view captures the mouse (`Hover` priority) while it is over one of its controls or a button pressed on it is held, and the keyboard (`Focus` priority) while a text box has the focus, so scripts don't see what the UI takes. A click where no control is gives the focus back to the game, and a game drag that crosses the UI stays with the game.

## Status and limits

This is the design in the analysis document up to Skia on Stride's own Vulkan device; Skia on Direct3D 12 comes next. The native Stride renderer has its first two steps.

- The native renderer is opt-in (`AvaloniaUIRenderer.Native`). It records Avalonia's drawing with Stride's own geometry, bitmaps and text. On the game's device it draws solid shapes and clips itself (see Using it) and hands every other call to the Skia package, which needs to be referenced. Its edges are anti-aliased as Skia's are on the GPU, so they differ a little from Skia's on the CPU, within the allowances the tests measure. On the CPU it draws the reference views (see Tests) pixel for pixel as Skia does on Windows and Linux. On macOS, Skia samples the scaled images of the `Images` page a little differently in the runs the native renderer hands it, which it draws at the origin of their own pixels, and the native project's `thresholds.jsonc` allows those pixels there. One difference is known: a `VisualBrush` or `DrawingBrush` that is stretched or scaled up looks softer, as its content is drawn at its own size and then scaled, where Skia draws it at the size it fills.
- Known limits of the native renderer on the device: a bitmap blending mode other than source over (`RenderOptions.BitmapBlendingMode`) in a call handed to the Skia package blends with transparency instead of what is under it. Borders of uneven thickness go to the Skia package until the native renderer draws paths. The shader draws one clip at a time: a turned or rounded clip inside another one goes to the Skia package with its content. A stroked ellipse has its exact ring, where Skia strokes it along curves that stay within about 0.15 pixels of it.
- Skia renders on the GPU with Vulkan only: with its Vulkan backend, and on macOS with its Metal backend, on the Metal device MoltenVK runs the game's device on. With Direct3D 11 or 12 and OpenGL, it renders on the CPU and each changed frame is uploaded whole.
- On macOS, the queue doesn't order Skia's Metal commands with the game's, as MoltenVK orders its own with Metal fences. So Skia waits for the queue to finish the game's commands before it draws a view, and for its own commands after: a frame that draws a view again waits for the GPU twice.
- Avalonia has one GPU in a process: it follows the device of the last game that loaded its graphics content.
- Avalonia's Skia GPU interface is internal: the platform implements it with runtime code generation, so where there is none (NativeAOT) Skia renders on the CPU.
- Text is anti-aliased in grayscale, as the views are drawn over the game (subpixel text needs an opaque background).
- Views are full screen overlays drawn after the scene; views in the 3D world (like `UIComponent`'s non full screen mode) are not done yet.
- Avalonia's colors are blended in sRGB and Stride's in linear: on an sRGB back buffer, anti-aliased edges can look slightly different from a desktop Avalonia app.
- Touch and pens act as the left mouse button, first finger only. Text input takes committed text; IME compositions in progress are not shown.
- Not yet: clipboard, cursors (the requested cursor type is in `StrideTopLevelImpl.Cursor` but the game's cursor doesn't follow it), editor support (the editor's scene view doesn't show the views). Popups (combo box lists, menus, tool tips) are not tested yet.
- The platform uses Avalonia APIs marked private or internal, so the package depends on the exact Avalonia version it was built with.

## Tests

`Stride.AvaloniaUI.Tests` runs a headless game with simulated input for the layout, rendering and input capture, and games on the GPU (Lavapipe on CI) that check the view is drawn over the scene and takes its clicks with Skia on the device and on the CPU, that both draw the same frame, and that the view is drawn again when it moves between them. `Stride.AvaloniaUI.Native.Tests` runs games with the native renderer, as Avalonia has one renderer per process. With `VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`, the Vulkan validation layer fails the GPU tests on any error.

`NativeCanvasTests` draws each reference page, and each shape case (`Stride.AvaloniaUI.Tests/Shared/ShapeCases.cs`: views of 240x160 pixels that each show one kind of shape or clip), natively and with the fallback alone. The native frame may have as many pixels more than 12 away from the fallback's as Skia on the GPU has from Skia on the CPU, which `SkiaEdgeAllowanceTests` measures in the Skia project (Linux, Lavapipe) and the shape cases and reference views keep as their allowances. Other systems and devices put a few more edge pixels beyond 12, so they get a tenth more (`EdgeAllowances`). Skia on Metal (macOS) draws some clip edges its own way: on the four clipped cases where it goes beyond that, `SkiaEdgeAllowanceTests` holds it to the counts of the macOS runner (`MetalEdgeCounts`), while the native renderer keeps the counts of Linux. The tests also check why the native canvas falls back: on each page, only for what a later step of the native renderer draws (`ReferenceViews.AllowedFallbacks`).

Both projects draw the reference views (`Stride.AvaloniaUI.Tests/Shared/ReferenceViews.cs`: nine pages of 640x480 pixels, from the Fluent controls to shapes, text, gradients, images, paths, clips, opacity and effects) and compare each frame with its gold image, `tests/baselines/<project>/<platform>.<API>/<device>/ReferenceViewTests.<Page>.png`. The golds are the frames of the whole-frame Skia renderer on the CPU. The native project holds copies of them, and `GoldTests` checks that they are the same files, so the native renderer is held to Skia's frames. The golds are made on Linux with Vulkan (Lavapipe), and on Windows with Direct3D 11, Direct3D 12 and Vulkan, where every API draws the same frames. Windows has its own golds for the two pages with the most text, `Fluent` and `Text`, as Skia draws glyph edges differently there; they are in the `Windows.Direct3D12` folder, which the other Windows APIs fall back to, and the other pages fall back to the Linux golds. macOS (Vulkan on MoltenVK, the Apple M1 runner) has its own golds for `Fluent`, `Text`, `Images` and `Clips`, in `macOS.Vulkan/Apple M1`, as Skia draws glyphs and scaled images a little differently there. They come from the macos-15 runner image; on macos-26 CoreText draws a few glyph pixels of `Text` differently, which both projects' `thresholds.jsonc` allow.

When a page or the Skia renderer changes, the golds are made again:

1. A local run of the Skia project's reference views, `dotnet test sources/plugins/AvaloniaUI/Stride.AvaloniaUI.Tests --filter "FullyQualifiedName~ReferenceViewTests"` (on Linux, with `-p:StridePlatforms=Linux -p:StrideGraphicsApis=Vulkan`), writes the frames that have no gold, or that differ from it, under `tests/local/Stride.AvaloniaUI.Tests/`, to look at. A page shows nothing that animates, so two runs give the same files.
2. The golds themselves come from CI, as for every graphics test (see the repository's `AGENTS.md`): run the `test-gold-gen.yml` workflow with the test filter `FullyQualifiedName~ReferenceViewTests` and the Skia project alone in `projects` (`sources/plugins/AvaloniaUI/Stride.AvaloniaUI.Tests/Stride.AvaloniaUI.Tests.csproj`), and commit its golds with the change that made them. Where the workflow can't land them (a fork without the Stride Bot app), run it with `update-gold` at `none` and promote its `gold-images` artifact locally with `dotnet run --project tests/infra/Stride.CompareGold -- promote --source <the unzipped artifact>`.
3. Copy the Skia project's `.png` and `.metadata.json` golds to the same folders under `tests/baselines/Stride.AvaloniaUI.Native.Tests/`, so that both projects hold the same files.
