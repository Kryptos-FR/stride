# Plugin model findings

What Tessera met in Stride's plugin model while being built as a third party would build it. Tessera never patches Stride: a gap is written here with what Tessera tried, what happened, the workaround kept inside Tessera, and the change suggested to Stride. A finding that blocks a feature leaves the feature out.

Tessera is the second extension of this kind, after [Skein](https://github.com/Kryptos-FR/stride/tree/feature/colorrise-skein/extensions/ColorRise.Skein). Where Tessera meets a point Skein already wrote about, the third table says only whether Skein's finding still holds. Tessera draws, which Skein did not: its findings are mostly about render features, batches, shaders and graphics tests.

Built on Stride's `master` at `659bb239e` (2026-11-24).

## Findings

| # | Plugin point | What Tessera tried | What happened | Workaround in Tessera | Suggested change |
|---|---|---|---|---|---|
| 1 | Graphics tests: the package `Stride.Dependencies.Lavapipe` (2026.10.12), the software Vulkan driver Stride's own graphics tests use | Reference it from `ColorRise.Tessera.Tests`, so that the tests draw without a GPU and without a window | It works: four tests draw and read their frames on Linux with `DISPLAY` unset. But every build of a project that references it warns NETSDK1206, because the package puts a second Linux driver under a made-up runtime identifier, `linux-x64-nodmabuf` | None: the warning is left visible | Put the second driver in a folder under `runtimes/linux-x64/native/` instead of under a runtime identifier of its own |
| 2 | Asset compilation in a test process: `PackageSession`, `PackageCompiler` and `Builder`, as Skein's tests compile Yarn projects | Build a tile map asset into a database inside `ColorRise.Tessera.Tests` | The first `PackageSession` throws `TypeLoadException: Could not load type 'DisposableWriteLock' from assembly 'Microsoft.Build.Framework, Version=15.1.0.0'`. `Stride.Core.Assets` keeps the runtime of the MSBuild packages out of its own output (`ExcludeAssets="runtime" PrivateAssets="all"`), but its `Microsoft.CodeAnalysis.Workspaces.MSBuild` brings `Microsoft.Build.Framework` 17.11.48 into the output of every project that references it. With SDK 10.0.404, `MSBuildLocator` then loads that old copy beside the SDK's MSBuild 18 | The test project references `Microsoft.Build.Framework` 17.11.48 with `ExcludeAssets="runtime"` | `Stride.Core.Assets` (or the dev package of it) carries the exclusion to its consumers, for instance with a `buildTransitive` target that removes `Microsoft.Build*.dll` from the copied runtime assets |
| 3 | Asset YAML: a member typed `object`, here the properties of a tile in the tile set asset (`Dictionary<string, object>` of bool, int, float, string and color) | Save the asset and load it back | A `float` comes back as a `double`, and strings that look like numbers or booleans (`"3"`, `"true"`) come back as an `int` and a `bool`. The serializer writes a primitive without a tag when its type is the default for the YAML scalar (`float` shares the tag `!!float` with `double`), and writes the string without quotes | The asset keeps its properties as typed values (`TileProperty`: `TileIntProperty`, `TileFloatProperty`, and so on), each with a tag of its own; the compiler turns them into the plain values of `Tile.Properties` | In a member typed `object`, write a tag for every primitive that is not the type the scalar reads back as, and quote a string that would read as another type |
| 4 | Textures built by a third party's compiler: the tile set compiler packs its tiles with `TexturePacker` and `AtlasTextureFactory`, reads images with `TextureTool`, and writes textures with `TextureHelper.ImportTextureImage`, as the sprite sheet compiler does | Use them from Tessera's `Assets` package | They work: all are public, and the asset compiler has the texture tools' native libraries. Two gaps: `TextureSerializationData.Version` is internal, so a third party's command cannot hash it and build its textures again when Stride's texture format changes, as `SpriteSheetCommand` does; and `TextureHelper.ImportParameters` has no constructor of its own, so the compiler makes a `TextureAsset` and a `TextureConvertParameters` only to get one | The command's version is raised by hand; the compiler makes the texture asset | Make `TextureSerializationData.Version` public, or give `AssetCommand` a way to add it to the hash; give `ImportParameters` a public constructor |
| 5 | Tests that read a texture a build wrote, without a graphics device | Load the tile set without its textures, then read a texture's pixels | `ImageTextureSerializer`, which reads a texture as an `Image`, is internal. `ContentManagerLoaderSettings.ContentFilter`, which keeps references from loading, is a public delegate whose parameter, `ContentReference`, is internal: only a lambda without parameter types can implement it | The test reads the texture's chunk itself (`ChunkHeader` is public) and gives the image to `Image.Load`; its filter is `(_, ref load) => load = false` | Make `ImageTextureSerializer` public, or let a content manager read a texture as an image; make `ContentReference` public |
| 6 | A game's compositor for a render feature that draws only in the transparent stage: a `ForwardRenderer` with a `TransparentRenderStage` and no `OpaqueRenderStage` | Draw a tile map in the game of the packages check | The first frame throws a `NullReferenceException` in `ForwardRenderer.ResolveDepthAsSRV`. The forward renderer makes its render targets and its depth buffer from the outputs of the opaque stage (`PrepareRenderTargets` returns at once without one), so the transparent stage finds no depth buffer to resolve. Nothing says that the opaque stage is required | The game's compositor has an opaque stage, which draws nothing | `ForwardRenderer` prepares its targets from the transparent stage when there is no opaque stage, or its validation says that the opaque stage is required |
| 7 | Graphics tests of a render feature with MSAA: a `ForwardRenderer` with `MSAALevel` X4, in a test process | The bleeding tests at 4 samples | The first frame fails: the forward renderer's `MSAAResolver` draws with `MSAAResolverShader`, an effect it compiles at run time, and a test process has neither the shader sources nor a database with that effect | The test harness has a renderer of its own for MSAA: it draws the stages into multisampled targets, then resolves them with `CommandList.CopyMultisample`. Games keep `ForwardRenderer` | A test kit for runtime plugins (Skein's finding 6) that gives a game the engine's effects, or the resolve shader as precompiled bytecode, as `SpriteEffect` has |
| 8 | Order in the game's transparent stage under a tilted camera: tile layers, and a sprite whose z is between two of them | Layers at depths of their own, each chunk a render object whose bounding box covers its 16 by 16 cells, all chunks of one place with the same centre | Layers keep their order under a tilted camera (a test checks it). A sprite between two layers does not, as the review of the branch found by reading the sort: `BackToFrontSortMode` orders render objects by the distance from the camera's plane to the centre of their bounding box. Under a tilt, that distance changes with y much more than with the small z between layers, so a sprite away from the middle of a chunk sorts before or after both layers, whatever its z. Tiles blend and do not write depth, so depth does not set the order right. With a camera that looks straight at the map, the distance is the z, and the order is right (a test checks it). `AxisSortTests` shows it under a camera tilted 30 degrees: with the default sort, a sprite nearer than the middle of the chunk covers both layers, and a farther one is covered by both | Step 2: `TileAxisSortMode`, a sort mode of Tessera's own (`SortMode` is public and made to be derived from), which orders the stage back to front along an axis of the world (Z by default) instead of by the distance to the camera's plane. A game sets it on the transparent stage of its compositor, by hand: a render feature or its provider cannot set it (finding 10). Everything in that stage sorts along the axis, which is right for flat things and wrong for a transparent 3D object that stands across the axis | A way for a render feature to give the stage the distance to sort an object by (for flat layers, the distance of the point under the sprite) |
| 9 | Content types of a plugin, cloned with an entity (`Entity.Clone`, `Prefab.Instantiate`) | A `TileMapComponent` whose map is content, cloned with its entity as the instances of a prefab are | Each clone got a copy of the map and of every tile set: `EntityCloner` shares only the types registered with `CloneSerializer<T>` in the `Clone` profile. Stride's own plugins register theirs (`Sound`, `Heightfield`, `PhysicsColliderShape`), but the plugin sample's content type (`samples/Plugin/Plugin/MyTemplate/MyTemplateData.cs`), which Tessera's content types copied, does not, and `docs/build/plugins.md` does not say so | `TileMap` and `TileSet` have `[DataSerializerGlobal(typeof(CloneSerializer<T>), Profile = "Clone")]`; a test clones an entity | Add the registration to the plugin sample's content type, and a line on it in `docs/build/plugins.md` |
| 10 | Render features that a plugin gives the compositors Game Studio makes (`IRenderFeatureProvider`: previews, thumbnails, a new game's compositor, "Add package features") | `TileRenderFeatureProvider` gives `TileRenderFeature`, whose selector puts the chunks in the transparent stage it is given | A provider makes render features and their selectors, and nothing else: it cannot set what the feature needs from the stage it draws in, here the sort mode of the transparent stage (`TileAxisSortMode`, finding 8). The stage keeps `BackToFrontSortMode`, so a sprite between two layers under a tilted camera sorts wrong in a compositor made by Game Studio until the game changes it | The README says to set `TileAxisSortMode` on the transparent stage of the game's compositor, by hand. Seen in Game Studio (step 2, Task 17): "Add package features" adds the feature with its selector, and the compositor editor offers "Back to front along an axis" in the sort modes of a stage | A provider (or a render feature) that can ask its stage for a sort mode, or set what it needs of the stage when the compositor is made |
| 11 | The test kit of editor plugins (`StrideEditorTestSession`): what Game Studio registers when it starts | Tessera's templates, which make their asset with an `AssetFactory<T>` (`!TemplateAssetFactory`), run as "Add asset" runs them; a tile map dropped in a scene, whose policy the scene editor looks for | "Unable to retrieve template generator for the selected template": both Game Studios register the generators of Stride's asset templates when they start (`StrideAssetTemplates.Register`, called by `StrideTemplates` and `StrideAvaloniaTemplates`), and the kit's session does not. The scene editor of a kit session has no drop policy of a plugin either: Game Studio's editor plugin (`StrideEditorPlugin`) registers the drop policies, entity factories and gizmos of each asset assembly, and the kit does not load it. A test that adds it to the session's plugins finds the policy, but the session then does not end: its background work is still running 30 seconds after it is destroyed. The kit's documentation says neither. Skein did not meet the first: its tests run the template of a Yarn project, whose generator Skein registers itself (Skein's finding 18) | The tests' session calls `StrideAssetTemplates.Register` before it runs a template, with prompts for scripts and models that refuse. The drop test calls `AddAssetPolicyRegistry.RegisterAssembly` with Tessera's editor assembly, as Game Studio's editor plugin does | The kit registers them when it opens a session (with prompts a test can set, like the kit's dialogs), or its documentation lists what a test registers itself |
| 12 | The session's property grid over objects that are not in an asset: an editor's `IPropertyProviderViewModel` whose root node comes from `AssetNodeContainer.GetOrCreateNode`, as Skein's node headers do | The tile set editor shows the data of the selected tiles in the grid (one copy of each tile's definition, several at once) and writes each change to the asset, in a step named `Tile data` | The grid edits the copies well: a string, a flags enum, and a dictionary of an abstract type (`AddPrimitiveKey`, then `CreateNewInstance` with the type), for one or several tiles. But the grid names the step after its own action, once the change is done (`AssetNodeViewModel.SetNodeValue` gives `Update property Kind`, `AssetNodePresenterCommandWrapper.Invoke` gives `Execute AddPrimitiveKey`), so a change the provider writes inside that transaction gets the grid's name, and a name given later does not reach the history panel, which reads it when the step is done | The copies' graph has no undo operations, so the grid's transaction stays empty and the history leaves it out. The editor writes the asset once that transaction is over (on the dispatcher, after `TransactionCompletion` when one is still open), in a transaction of its own named `Tile data`, with every copy that changed | A provider can name the steps of the changes made through it (for example a name asked of the provider for the grid's transaction), or the grid keeps a name already given to its transaction |
| 13 | Shortcuts of a plugin's commands (`CommandDescriptor`, `CommandGestureBindings`) | Give the tools of the map editor single keys, as other tile editors do (B, P, F, E, I, R, X, Y, Z), as the default shortcuts of Tessera's commands | `CommandGestureBindings` refuses a shortcut without Ctrl, Alt or Meta, unless its key is F1 to F24, so that a plain key stays with the text boxes. The editor's own defaults are exempt, but a plugin's are not. So a plugin cannot have a command whose default shortcut is one key, even one that only runs while its own control has the focus | The map canvas reads the keys itself (`TileCanvas.OnKeyDown` gives them to the tools) while it has the focus, and not while a name is typed in the layer list. The commands are still in the palette, with the key in their keywords, but the keys cannot be rebound in the settings | A command whose shortcut runs only while a control of the plugin has the focus (a gesture scope of the plugin's view) may have a single key, as the editor's own defaults may |
| 14 | A compiler's input types (`GetInputTypes`) with `BuildDependencyType.CompileAsset` | The tile set's compiler reads the sprite sheets of its sheet sources as assets (`CompileAsset`), as it needs their sprites and not their content | `AssetDependenciesCompiler.Prepare` prepares a node once, at the first link that reaches it, and compiles it only when that link is `Runtime` or `CompileContent`. In the check game, the scene's first entity shows a map, so the build reaches the sheet `Props` through the map and the tile set first (`CompileAsset`, not compiled), then through the sprite of `Hero` (`Runtime`), where the node is already visited. The sheet is never compiled, and the bundles fail: "Could not find content [/StudioCheck/Sprites/Props], referenced by [/StudioCheck/MainScene], for bundle default: nothing compiled it". The same scene with the sprite's entity first builds | The tile set's compiler declares the sheets `CompileAsset` and `Runtime`, so the first link compiles them. A sheet used only by tile sets is compiled and packed in the game anyway, and its textures with it | `Prepare` compiles a node it visited through `CompileAsset` alone when a later link needs its content (`Runtime` or `CompileContent`). The tile set's compiler then goes back to `CompileAsset` alone |
| 15 | The scene editor's reload of a changed asset (`EditorContentLoader`) | The scene view follows a map changed and saved in the map editor (R5) | It works without anything from Tessera: the editor builds the changed map, unloads the old `TileMap`, loads the new one and gives it to the component, whose processor already handles a new map. But the reload that keeps the same object (fast reload) is a closed list of engine types (`EditorContentLoader.FastReloadTypes`: materials, textures, normal maps), with a `TODO` for an attribute; a plugin's content type cannot join it | None needed: `TileMapComponent` takes the new map. Seen in Game Studio (step 2, Task 17, line 10). Step 3's flipbooks met it too (R13): a flipbook changed in its editor while its scene is open shows in the scene view at once, before the save, and `FlipbookComponent` takes the new flipbook with no code of Tessera's for it (step 3, line 16 of the studio check) | An attribute (or a registration of the plugin) that lets a plugin's content type be fast reloaded, as the `TODO` of `FastReloadTypes` says |
| 16 | The scene editor's picking stage (`EditorGameEntitySelectionService`) | A click on a map in the scene view selects its entity (R7) | The selection service makes the stage `Picking` and gives it to the features it knows by type: it adds selectors to `MeshRenderFeature` and `SpriteRenderFeature` only. A plugin's render feature is not drawn in the picking stage, so a click on a map selects nothing | `TilePickingService`, an editor game service of the scene editor at `Order = 210` (after the selection service's 200), adds a `TileTransparentRenderStageSelector` on the last stage named `Picking` to `TileRenderFeature` and, since step 3, to `FlipbookRenderFeature` (each feature once, whichever the compositor has). Both draw each tile in the id of its component (`RuntimeIdHelper.ToRuntimeId`) when the stage is named `Picking`. It depends on the stage's name and the service's order, neither of which is public API. Seen in Game Studio (step 2, Task 17, line 11) | The selection service asks the render features for their picking, for example through an interface that a feature implements to add its selector to the picking stage it is given |
| 17 | A plugin's render feature saved in a compositor asset (`RenderFeature` has `[DataContract(Inherited = true, DefaultMemberMode = DataMemberMode.Never)]`) | `TileRenderFeature` had its own `[DataContract("TileRenderFeature")]`, for a short tag in the YAML | The derived class's contract gives every public member by default, so the compositor saved the base class's runtime state (`RenderData`, `RenderObjects`, `ObjectNodeReferences`, `RenderNodes`) and `Enabled`, whose setter throws `NotSupportedException`. Once the scene was opened again, its view drew nothing (no sprite, no gizmo), with no message in Game Studio's output, until these lines were removed from the file by hand | `[DataContract("TileRenderFeature", DefaultMemberMode = DataMemberMode.Never)]`, as `MeshVelocityRenderFeature` does, with a test that saves a compositor and looks for the members | `Enabled` and the runtime collections of `RenderFeature` marked `[DataMemberIgnore]`, so that a derived contract cannot save them; or a warning when a compositor fails to load |
| 18 | One render feature for two kinds of render object (`RenderSystem.AddRenderObject`) | One feature drawing the chunks of maps and the frames of flipbooks, both with `TileBatch` (design, section 8) | The render system finds the feature of a render object by the object's exact type (`renderObject.GetType()` in its table of features by type), so a root render feature draws one class of render objects and no subclass | Two features: `TileRenderFeature` ("Tile maps") draws `RenderTileChunk`, `FlipbookRenderFeature` ("Flipbooks") draws `RenderFlipbook`; they share `TileBatch`, `TileBatchRun` and the stage selector. A game's compositor needs both, and `TileRenderFeatureProvider` gives both, so *Add package features* adds the one a compositor lacks | A look-up of the feature that accepts a base type (or an interface) of the render object, so that a plugin with several kinds of render object can keep one feature in a compositor |
| 19 | The property grid of the cross-platform Game Studio: a `[Flags]` enum (`TileFlip` of a cell and of a frame's cell, `TileCollision` of a tile) | Set a flip in the grid, as the WPF Game Studio does with its list of check boxes | The Avalonia template `FlagEnumTemplateProvider` (`DefaultPropertyTemplateProviders.axaml`) shows a check box for each value, but the list's selection is bound to nothing: a box ticked shows no state and writes no value; only *All*, *None* and *Invert* write (the WPF template binds the selection with `ListBoxBindableSelectedItemsBehavior`). Seen in step 3, line 7 of the studio check | `TesseraEditorAvaloniaPlugin` registers `TesseraPropertyTemplateProviders`: for `TileFlip` and `TileCollision`, a template that overrides `Enum` and `FlagEnum` with `FlagsBox`, a check box for each one-bit flag, bound both ways to the node's value | Bind the template's selection to the node's value in Game Studio, as WPF does, and Tessera's template can go |
| 20 | The property grid of the cross-platform Game Studio: an enum whose values have a `[Display]` name (`FlipbookDirection` of a clip and of a flipbook component) | Show "Any direction" and "Down left" in the grid, as the flipbook editor does | The list shows each value by its name in the code (`None`, `DownLeft`), and so do Stride's own enums (`GraphicsProfile` shows `Level_10_0`). `EnumComboBoxTheme` (`DefaultPropertyTemplateProviders.axaml`) has an item template that reads the `Display` name with `EnumToDisplayName`, but the template is typed `NodeViewModel` while the items are the enum's values, which is most likely why it is not used: the WPF template, the same without a type, is used. Seen in step 3, line 14 of the studio check | None in the grid: the editor's tree, its problems, its questions and its lists name the directions with `FlipbookDirections.NameOf`. The `Display` names are kept for the WPF Game Studio and for the day the Avalonia list reads them | Type the item template of `EnumComboBoxTheme` for the enum's values (or leave its type out), so that each value shows its `Display` name |
| 21 | The property grid of the cross-platform Game Studio: the list that picks the type of an abstract value (a property of a tile in the tile set asset, a `TileProperty`: `None`, `Bool`, `Int`, `Float`, `String` or `Color`) | Give a new property of a tile the type `String`, as Thornwick's bush and doors need | The list opens with dark text on an almost black background: its names can only just be read (`studio-04-type-list.png` of step 4). `AbstractTypeSelectionComboBoxTheme` (`DefaultPropertyTemplateProviders.axaml`) gives its drop-down the fixed background `#101011`, made for a dark theme, while its items take the theme's text colour, which is dark in the light theme Game Studio runs in. ## Tied to the fork

Tessera is meant to move to a repository of its own. What still depends on the checkout it sits in, and what Stride would have to publish to remove it:

| # | What | Why | Goes when |
|---|---|---|---|
| T1 | `nuget.config` has a source `stride-dev` pointing at `../../bin/packages` | The Stride packages with the plugin model exist only as the output of a local engine build | A released Stride has the plugin model; nuget.org then serves the packages |
| T2 | `Directory.Build.targets` names the asset compiler under `$(StrideRoot)sources/assets/Stride.AssetCompiler/bin/` | Skein's finding 1. Only in dev-redirect builds, from properties the dev package stubs set; nothing is read from the tree by Tessera itself | Skein's finding 1 is fixed, or Tessera builds against published packages |
| T3 | Tessera's packages depend on a prerelease Stride (4.5.4-dev), so they have a prerelease version too (0.1.0-dev); a stable version on a prerelease dependency makes `dotnet pack` warn NU5104 | No released Stride has the plugin model | A released Stride: Tessera then gets a stable version |
