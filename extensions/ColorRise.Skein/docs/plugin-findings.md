# Plugin model findings

What Skein met in Stride's plugin model while being built as a third party would build it. Skein never patches Stride: a gap is written here with what Skein tried, what happened, the workaround kept inside Skein, and the change suggested to Stride. A finding that blocks a feature leaves the feature out.

Based on `feature/xplat/plugin-follow-ups` (17f6ee7d7, 2026-11-15).

## Findings

| # | Plugin point | What Skein tried | What happened | Workaround in Skein | Suggested change |
|---|---|---|---|---|---|
| 1 | Building a plugin against a local engine build | `dotnet pack` (Release by default) of the solution after a Debug engine build | `Stride AssetCompiler could not be found (.../Stride.AssetCompiler/bin/Release/net10.0/Stride.AssetCompiler.dll)`: the asset compiler's targets look for the compiler in the project's `$(Configuration)`, while the dev package stubs take every assembly from the engine's (`$(StrideDevConfiguration)`). Saga's finding 2, still there on 17f6ee7d7 | `Directory.Build.targets` sets `StrideCompileAssetCommand` from `$(StrideDevConfiguration)` in dev-redirect builds (T2 below) | `_StridePrepareAssetCompiler` could use `$(StrideDevConfiguration)` when it is set, as the stubs' references do. Dev workflow only; published packages are not affected. |
| 2 | Restoring a project that references Stride's packages | `dotnet build` of the solution | Each project gets NuGet's vulnerability warnings NU1902 and NU1903 for `SixLabors.ImageSharp` 3.1.12, which Stride's packages bring; a third party that builds with warnings as errors must silence them | None: the warnings are left visible | Stride could move to a fixed ImageSharp, or keep it out of the packages a plugin references. |
| 3 | Asset templates (`TemplateAssetFactory` in an `.sdtpl`) | A template with `DefaultOutputName: Dialogue`, used by *Add asset* in a folder named `Dialogue` | The asset view shows the new asset in the folder, but its location is `Dialogue` at the root and it is saved as `Assets/Dialogue.yarn`: `AssetTemplateGenerator.GenerateLocation` takes a name that starts with the target folder's path for a full location (`assetName.StartsWith(parameters.TargetLocation)`). Stride's own templates do the same (a "Material" in a folder `Material`) | The template's default name is `YarnScript`, which is unlikely to be a folder's name | `GenerateLocation` could compare whole directory segments, or always combine the folder and the name. |
| 4 | `SourceCodeAsset` for a third party's text format | Saving a `.yarn` script whose text was loaded or changed | The file gets a UTF-8 byte order mark (`DefaultTextAccessor.Save` writes with `Encoding.UTF8`), whatever the file had; a file never read is copied as it is. Yarn Spinner's tools write no mark, so every script touched in Game Studio shows a change of its first bytes | `YarnScriptAsset` overrides `Save(Stream)`: UTF-8, with a mark only when the file came with one | `DefaultTextAccessor` could keep what the file had, and write no mark for a new file. |
| 5 | Editor test kit (`Stride.Assets.Editor.Testing`) | Three xUnit test classes that each open kit sessions, run as xUnit runs them by default (classes in parallel) | The test run hangs, with no failure and no message: the kit's sessions share one dispatcher and process-wide registries. Two classes had passed, so it showed up late. Stride's own test projects turn parallel runs off, but the kit's documentation does not say a plugin's tests must | `[assembly: CollectionBehavior(DisableTestParallelization = true)]` in `ColorRise.Skein.Editor.Tests` | Say it in the kit's documentation, or have the kit fail with a message when a second session opens from another thread while one is open. |
| 6 | Testing a runtime plugin (a game system, components, scripts) without a window | Tests that make a `Game`, never run it, give it a scene and step `game.Script.Update(...)` by hand, as Stride's own `ScriptSystemTests` do | It works, and the game makes the plugin's `[GameSystem]`. One thing is out of reach: code that reads the game's clock (`Game.UpdateTime`, as a script's `Game.UpdateTime.Elapsed`) sees no time pass, because `GameTime.Update` is internal and `Game.UpdateTime` has no setter. A `<<wait>>` that counts game time cannot be tested through public API | The test harness calls `GameTime.Update` by reflection (tests only, `tests/ColorRise.Skein.Tests/Engine/GameHarness.cs`) | A public way to step a game's time in tests: for example a test kit for runtime plugins beside the editor's, with a game whose frames a test steps (`Step(TimeSpan elapsed)`). |
| 7 | Asset compilers (`AssetCommand<T>` of a third party's asset) | A build command with the constructor every command of Stride has (`url`, `parameters`, `assetFinder`, and what it compiles) | The build warns `STRDIAG010: The Type 'YarnProjectCommand' doesn't have a public parameterless constructor, which is needed for Serialization`: commands are data contracts (the build engine can send one to another process), and Stride's serialization analyzer runs on a plugin's project while Stride's own projects, whose commands are written the same way, do not run it | The warning is silenced on the command (`#pragma warning disable STRDIAG010`), with the reason | The analyzer could leave `Command` types alone, or the documentation of asset compilers could say what a third party's command needs. |
| 8 | Editor test kit (`Stride.Assets.Editor.Testing`), session services | A session service registered in `InitializeSession` (`context.Services.Register`) that stops its background work in `context.OnClose`, in a test opened with `InitializeSession = true` | The kit destroys the session but never disposes the plugin host it made, so the `OnClose` actions do not run: the service goes on after the test's session is gone, and the teardown waits (up to its 30 seconds) for work the service tracked with `TrackBackgroundWork` | Skein's tests wrap the kit's session and close Skein's services before they dispose it (`SkeinSession.DisposeAsync`) | `StrideEditorTestSession` disposes its `TestPluginHost` when the session is disposed, before it waits for the background work, as the editor does when it closes a session |
| 9 | Editor test kit (`Stride.Assets.Editor.Testing`), dialogs | A test of a service that asks the user a question (a message box with two buttons) | The kit gives `NotSupportedService<IEditorDialogService>`, which throws on every question. The fake that Stride's own tests answer with (`FakeEditorDialogService`) is in a test project, not in the kit, and the interface is large (dialogs, pickers, and the progress window the session shows when it opens) | The test writes a `DispatchProxy` of `IEditorDialogService` that answers `MessageBoxAsync` and ignores the calls that return nothing (`ExternalChangeTests.Dialogs`) | The kit could ship a dialog service whose answers a test scripts and whose questions it records |
| 10 | `SourceCodeAsset` for a third party's text format, changed by another program | A `.yarn` file rewritten by another tool while Game Studio has the project open | Nothing happens: the session's reload of assets changed outside skips every `SourceCodeAsset` ("code files are reloaded by their own editor", `ExternalAssetChangeTracker.ProcessFile`), and there is no hook for the owner of the format. A script with no editor open is never read again, though its text is what the project compiles and what the next save writes | `YarnExternalChangeService` watches the asset folders itself (`DirectoryWatcher`), reloads through the script's text buffer, and knows what the session wrote from `YarnScriptAsset.SavedText`, since the session's own record of it (`NotifySaved`) is internal | The tracker could give the change to the asset's view model (a virtual method the owner overrides), with its watcher, its quiet delay and its knowledge of what the session saved |
| 11 | Node graph control (`NodeGraphControl`, experimental) | A graph whose links are of two kinds (a jump, and a detour that comes back), with links to nodes that do not exist, and frames around groups of nodes | The control draws every link with one brush and one thickness (`LinkBrush`, `LinkThickness`): a link cannot be dashed or red. It has no layer where a plugin draws in graph coordinates, under or over the nodes. Its own "show all" (`FitToView`, the Home key) knows the nodes only, so what a plugin draws around them is cut | A detour has its own output connector on a card, and a broken link ends at a red stub. The frames are a control under the graph, whose background is transparent, that reads `Zoom`, `Offset` and the nodes' bounds (`YarnGraphDecorations`). Skein has its own "show all the nodes" with room for the frames (`YarnGraphBinding.FitToView`) | A style for a link from its data (a template or a selector for the brush and the dashes), a layer for a plugin's drawing in graph coordinates, and a margin for `FitToView` |
| 12 | Editor test kit (`Stride.Assets.Editor.Testing`), views | A headless test of a plugin's view (`[AvaloniaFact]` of Avalonia.Headless.XUnit) on a view model of a kit session | The kit's dispatcher is its own (a lock, with posted work on pool threads), not the toolkit's UI thread: awaiting the kit inside the test leaves the UI thread, and what the session's services post reaches the view from another thread. The kit says nothing about views | `ScriptView` (in `ColorRise.Skein.Editor.Avalonia.Tests`) opens the session on a pool thread and waits, stops the background analysis once it has run, and does each step inside `session.Dispatcher.Invoke` on the UI thread, followed by `Dispatcher.UIThread.RunJobs()` | The kit could offer a session whose dispatcher is the toolkit's UI thread, for tests of views |
| 13 | A test program that references Stride's packages (xunit.v3 makes a test project an `Exe`) | Building the view tests, an `Exe` project that references `Stride.Assets.Editor.Testing` | Stride's asset compiler targets take every `Exe` for a game and compile its assets: the build fails with "Could not find game settings asset" | `<StrideCompilerSkipBuild>true</StrideCompilerSkipBuild>` in the test project | The targets could act only for a project that has a Stride package (`.sdpkg`), or the kit's documentation could name the property |

## Tied to the fork

Skein is meant to move to a repository of its own. What still depends on the checkout it sits in, and what Stride would have to publish to remove it:

| # | What | Why | Goes when |
|---|---|---|---|
| T1 | `nuget.config` has a source `stride-dev` pointing at `../../bin/packages` | The Stride packages with the plugin model exist only as the output of a local engine build | A released Stride has the plugin model; nuget.org then serves the packages |
| T2 | `Directory.Build.targets` names the asset compiler under `$(StrideRoot)sources/assets/Stride.AssetCompiler/bin/` | Finding 1. Only in dev-redirect builds, from properties the dev package stubs set; nothing is read from the tree by Skein itself | Finding 1 is fixed, or Skein builds against published packages |
